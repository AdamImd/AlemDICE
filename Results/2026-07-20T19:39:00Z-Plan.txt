  # Bodyless Team-Leader Pilot

  ## Summary

  - Create branch experiment/bodyless-team-leader from the current commit, preserving and never staging
    the existing edit to Results/2026-07-20T18:09:00Z-results.txt.

  - Implement three matched conditions:
      1. baseline: three workers with existing peer broadcasts and no leader.
      2. leader_peer: three workers plus a bodyless leader; worker reports also reach peers.
      3. leader_no_peer: three workers plus the leader; worker reports reach only the leader.

  - Run one Easy episode with seed 9999 and a 200-step evaluator cap per condition. Keep the environment/
    prompt horizon at 10,000 steps and allow natural early termination.

  - Produce a standalone Markdown and JSON results report; leave AAAI/main.tex unchanged.

  ## Interfaces and Runtime Behavior

  - Keep alem.num_agents=3 in every condition. The leader receives no environment observation slot, body,
    inventory, action, reward, Give target, trajectory row, or debrief.

  - Add a topology setting with the exact values baseline, leader_peer, and leader_no_peer, plus leader
    settings for client index 3, replanning interval 5, and zero semantic retries.

  - Extend the agent factory with a leader constructor using clients[3]; ordinary workers continue using
    clients[0:3].

  - Represent routed traffic with typed envelopes containing sender, recipients, channel, content, sent
    step, and delivered step. Use numeric leader ID 3 internally and display it as “Team Leader.”

  - Preserve the baseline worker prompt, action parsing, one-tick peer-message delay, and execution path
    byte-for-byte apart from additive instrumentation.

  Each leader tick—steps 0, 5, …, 195—will run in this order:

  1. Deliver eligible peer messages produced on the previous tick.
  2. Build the three workers’ normal long- and short-term legal text observations.
  3. Give the leader those rendered observations, worker reports accumulated since its previous call, its
     last valid plan/private scratchpad, and the same progressively disclosed public game rules. Never
     expose raw symbolic observations, environment state, hidden maps, debug metadata, worker scratchpads,
     or private reasoning.

  4. Parse the leader’s atomic whole-team plan and deliver each worker the shared objective plus only its
     own assignment before that tick’s worker call.

  5. Call the three workers concurrently and send only their three actions to env.step.
  6. Route their single <communication> payload for the next tick and accumulate it for the next leader
     review.

  The leader will return:

  {
    "objective": "non-empty string",
    "assignments": [
      {"agent_id": 0, "subgoal": "non-empty string", "milestones": ["1–5 strings"]},
      {"agent_id": 1, "subgoal": "non-empty string", "milestones": ["1–5 strings"]},
      {"agent_id": 2, "subgoal": "non-empty string", "milestones": ["1–5 strings"]}
    ]
  }

  - Wrap this JSON in <team_plan> and allow a private <scratchpad> capped at 1,000 characters.
  - Require exactly one assignment for IDs 0, 1, and 2; reject malformed JSON, duplicate/missing/out-of-
    range IDs, empty fields, or invalid milestone lists as one invalid whole plan.

  - Persist the last valid assignment between reviews and inject it into each worker prompt every tick.
    Count the assignment as network delivery only when issued, while measuring repeated prompt-injection
    bytes separately.

  - On an invalid plan, retain the previous valid plan. Before the first valid plan, use: “Use local
    judgment, survive, maximize achievements, and report blockers.” Clear the bounded report buffer after
    each completed scheduled leader response, even if parsing fails. A leader transport failure follows
    the existing episode-failure/resume policy.

  - In leader_peer, the worker’s parsed payload goes to the leader and both peers. In leader_no_peer, it
    goes only to the leader. This routing and the corresponding instruction text are the only differences
    between those leader arms.
